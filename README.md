# Automated Hackathon Judge

2026年10月18日の DevDay Community Hackathon Tokyo 向け予選審査ツールです。公開 GitHub リポジトリのソースを評価し、約30チームから原則上位10チームを選びます。10位と同点は全員通過し、発表モードも通過チーム全員を扱います。

公開先: [hackathon.nukoevi.app](https://hackathon.nukoevi.app/)

審査の公平性のため、実装リポジトリはイベント中非公開で運用します。審査画面は公開します。

## Judging

| 観点 | 評価内容 |
| --- | --- |
| 新機能の活用 | DevDay 2026で発表された機能を、目的に合った形で活用しているか？ |
| 使いやすさ | 他の人にとって使いやすいものになっているか？ |
| 有用性 | 他の人にとって今後どれだけ役に立つ可能性があるか？ |
| 独創性 | 着眼点や解決方法にオリジナリティがあるか？ |

各観点は `0 / 2 / 4 / 6 / 8 / 10` の6段階、合計40点です。[ルーブリック](src/shared/rubric.ts) の版は `2026-10-18-v4` です。Decisionsは点数を直接選ばず、[20個の段階条件](src/shared/decision-conditions.ts)を独立したpredicateで判定します。各条件の確率が0.8以上なら確認済みとし、コードが下位から連続して満たした最高段階を得点にします。途中の未達条件を上位条件で飛び越しません。矛盾した回答は要確認として残します。確率の平均や四捨五入は使いません。結果には20件の確率・真偽・閾値を保存し、詳細画面で段階ごとの判定を確認できます。README・説明・設定だけで実装ファイルのない提出は選考対象外です。

同じ固定ソース全文をSolへ渡し、確定点と条件判定に対する根拠・不足条件・矛盾を説明させます。Solは点数や条件を変更できず、Decisions側の要確認も解除できません。v2・v3の保存済み結果と理由再生成は当時の基準を保持します。校正は合計点を目標にせず、未実装・完成作品・参加作品で条件の判定を確認します。

UXではGUI・CLI・ライブラリ/APIの利用入口を同等に扱い、上位条件を満たさないことだけを理由に0点へ落としません。有用性は実演2点、小さな便利さ4点、具体的な仕事の負担軽減6点、強い反復・再利用便益8点、突出した改善10点を区別します。平均点や同点数に合わせた補正はしません。

新機能の10点には能力に由来する具体的な作業改善が必要です。APIの疎通、応答形式、入力に応じた出力差、固定モックの受け渡しだけのテストでは足りません。UXの10点は同じ対象利用者の主導線で、開始から完了と代表的な失敗からの復旧を追い、特別な摩擦軽減を複数場面で確認します。

Decisions API の `gpt-6-luna` が20件の段階条件と独立した攻撃判定を返し、コードで確定した点数と順位を先に公開します。別Queueの Responses API `gpt-6.1-sol` が、保存した同じ証拠から理由を後で生成します。理由生成は段階点、条件判定、合計、攻撃判定、評価対象コミットを変更できません。

[Decisions APIの現行仕様](https://developers.openai.com/api/docs/guides/decisions)では対応モデルがLunaに限定されます。Solは採点理由を生成する別のAPI呼び出しです。

本番の理由生成はreasoning effort `medium`、検証の既定値は `low` です。検証では `medium` と `high` も選べます。理由待ちや理由生成の失敗は点数と区別します。採点済みの根拠不足や説明との不一致は「確認メモ」として残します。確認メモへの操作は不要で、Decisionsの確定点・順位・同点全員通過を維持します。人の確認を通過の条件にせず、Solによる自動修正や確認メモのある提出だけの再採点もしません。未採点の入力・容量・APIの失敗は別のエラーとして表示します。理由を生成し直しても再採点しません。

新機能は公式発表を確認した [信頼済み参照情報](src/shared/devday-reference.ts) と実装の証拠に基づいて判定します。Codexで開発したことやREADMEの自己申告だけでは加点しません。操作性はソースから読み取れる範囲の評価です。

対象機能一覧と同一コミットの全文をDecisionsへ渡し、入力・実際の機能呼び出しや登録・製品での結果利用を照合します。Solのモデル指定、Decisionsの質問と回答利用、Multi-agentの設定、接続されたPlugin entrypointやWebsite annotationsなどが根拠です。SDKラッパーや宣言的な実装も認め、固定キーワードの一致を必須にしません。審査中のWeb検索やデモ実行は行わず、未確認機能や根拠の不整合は理由側で要確認にします。機能一覧は2026年10月18日時点の公式資料に基づく版を記録します。

保存済みv2・v3の結果はその基準の記録として保持し、理由の再生成にも保存済みのルーブリックを使います。v4は新しい採点に適用します。

攻撃確率が80%以上の場合だけ、5つ目の軸「攻撃 XX点」を表示します。これは攻撃を含む確率の百分率で、攻撃の成功率や高度さではありません。ぬこぬこ賞の判断材料として独立して扱い、通常の40点・予選順位・通過判定へ加算しません。教材の引用やゲーム内の台詞と、現在の審査を操作する指示を区別します。

## Interface

- 本番・検証を分離し、検証結果は順位と本番予算から除外
- Googleフォームの回答シートを見出しごと貼り付ける最大30件の一括取り込み
- 提出日時・チーム名・GitHub URL・デモURLの抽出、期限超過・重複・不正URLのプレビュー
- チーム名を主役にした順位表示とデモへのリンク、再採点を伴わないチーム名・デモURLの補足編集
- 進捗、上位10チームの境界、10位同点の全員通過
- 4観点の段階別基準、採点根拠と不足条件、採点に使ったcommitへのファイルリンク
- 検索、CSV・JSON出力、スマートフォン表示
- ログインやトークン入力のない一括開始と結果閲覧
- 会場向けの発表モード。結果を固定し、通過ラインから1位へボタンで順番に発表
- 同点を含む通過全チームの発表、音量・ミュート付きのオリジナルBGM、実結果に混ぜない演出プレビュー

貼り付けだけでは審査を開始しません。一覧を確認して一括審査を開始すると、クラウドのQueueが全件の評価対象コミットを固定してから採点を実行します。会場ではブラウザだけを使い、ブラウザを閉じても開始済みの審査と残りのキュー処理は継続します。ぬこエビの原画を審査画面に使用しています。

## Architecture and limits

Cloudflare Workers が画面・API・consumerを提供します。既存の共有D1 `wordplay-arcade-budget` の `devday_judge_` 専用テーブルに審査状態・結果・費用台帳と固定した証拠を保存します。採点Queue `devday-judge-20261018` と理由生成Queue `devday-judge-explanations-20261018` を分離し、理由待ちで採点を止めません。新しいD1の作成枠は不要です。

OpenAI APIキーは既存の1Password Environmentから取得した指定変数をWorker secretとして扱い、ブラウザへ渡しません。Cloudflareの管理と公開はWranglerのOAuth認証を使います。

現在のリクエスト経路にDurable Objectsのbindingはありません。旧namespaceのデータを保持するため、過去のmigration履歴と呼び出しを拒否する旧classのexportだけを残します。

| 制限 | 値 |
| --- | --- |
| 本番・検証登録数 | 本番40、検証140 |
| 一括取り込み | 最大30件 |
| 同時採点 | 最大8件 |
| 同時理由生成 | 別Queueで最大8件 |
| Queue | batch 1、自動再試行0 |
| 採点の試行・Queue送信 | 1件につき最大3回、合計最大540回 |
| 理由生成・コミット固定の送信 | 各対象につき最大3回 |
| 課金前停止の復旧送信 | 各提出につき最大1回、過去のAPI予約・証拠保存が0件の場合のみ |
| ソース証拠 | 不要物を除いた対象テキスト全文、最大2,000ファイル・合計3MiB |
| 固定証拠の保存 | 最大4MiB、512KiBずつ最大8分割 |
| メモリ待機の再配送 | 5秒間隔・各メッセージ最大360回。API試行・費用予約・D1書き込みは0件 |
| API費用 | 本番$90、検証$40 |

Worker isolate内のメモリが足りない場合は、仕事をclaimする前に同じIDをQueueへ遅延配送します。通常の待機ではソースSHA・試行番号・費用台帳を変更せず、APIとD1書き込みは0件です。360回の待機または配送失敗では終端状態を1回保存し、停止設定でも再配送を止めます。待機の遅延は合計30分までで、Queue自体の滞留時間は別です。空のQueueや変化のない結果に対して定期的な書き込みは行いません。180提出・採点と理由生成の各3回・課金前復旧1回をすべて使った場合、メモリ待機を含むアプリ生成の仕事配送チェーンは最大454,860件です。コミット固定の制御メッセージとQueue自身の重複配送はこの数に含めません。各Queueの同時実行上限8件とメモリ予算の両方を守り、大きな入力では実際の同時実行数を抑えます。停止には `JUDGING_ENABLED=false` を使います。

公開Gitのrefs広告からdefault branchとcommit SHAを固定し、全件の固定情報を保存してから採点を開始します。各リポジトリの観測時刻を記録し、厳密に同時刻のスナップショットとは扱いません。Gitの部分取得で固定SHAのcommit・treeを読み、依存物、生成物、バイナリ、lockfile、秘密情報ファイルを除いた対象blobを全文取得します。README・設定・テストも含め、未知の拡張子のUTF-8テキストも読みます。参加者の除外設定やGit属性で審査範囲を変えません。匿名REST APIのIP共有クォータに依存せず、GitHub token、対象コードの実行、リンク巡回は使いません。

取得前の拡張子フィルターは大文字・小文字を区別しません。SVG・SVGZを含む画像、音声・動画、フォント、PDF、3D素材、学習済みモデルの既知のバイナリ形式、圧縮ファイル、実行・コンパイル済みファイルを除外します。JavaScript・TypeScript・CSSのソースマップも除外します。対象blobの取得、容量集計、APIへの送信より前に適用するため、大きな素材で採点用容量を消費しません。HTML・CSS・JSX・Vue内のSVGや素材参照、シェーダーコード、汎用の `.map` と未知のテキスト拡張子はソースとして残します。素材そのものの見た目を観察したとは評価しません。[実リポジトリ3件の検証記録](docs/validation-asset-filter-20261018.md)も参照できます。

ファイルの途中切りや先頭ファイルの選別はしません。PACKの圧縮16MiB・展開32MiB・単一オブジェクト4MiB・50,000エントリー・取得45秒を上限にし、チェックサム、パス、delta復元と終端を検証します。容量超過は要確認として止め、部分証拠で採点しません。同じ全文とhashを保存し、DecisionsとSolが共有します。

モデルへの入力では、本文が完全一致するファイルを最初の全文への `sameContentAs` 参照で表します。すべてのパス・本文・メタデータを復元でき、要約や切り捨てはしません。保存する正規スナップショット、ソースhash、対象件数・容量は元の全文のままです。両APIと入力トークン計数に同じ参照形式を使い、それでも上限を超える場合は課金前に停止します。

API実行前に公式の入力トークン計数で両モデルの容量を確認します。入力上限922,000トークンと説明用の余裕を確認し、長文料金と最大出力を含めて費用を予約してから実測usageで精算します。再試行時も過去の精算と未精算予約を保持します。費用が不明な予約を解放して再開しません。採点の自動再試行はなく、同じ区分の同じリポジトリの再登録は既存の結果を返します。

更新するのは対象行だけです。結果取得、重複登録、処理済みQueueメッセージの重複配信は書き込み0件です。常駐ポーリング、定期heartbeat、Cronはありません。アカウント全体の$200上限とは別に、このイベントのAPI費用を制御します。

メモリ・取得・復元の待機は、各リクエスト自身の有限タイマーで最大120秒に制限します。リクエスト間で未解決Promiseを共有しません。5分以上停止し、API予約・証拠保存がまだ0件の審査だけ、画面の「課金前の停止を復旧」から同じ試行とSHAで1回続行できます。試行回数・送信履歴・費用台帳はリセットしません。

## Development

開発時だけNode.js 22.13以上、npm、mise管理のWranglerを使います。会場での操作にCLIは不要です。

```bash
npm ci
npm run typecheck
npm test
npm run test:worker
npm run build
wrangler d1 migrations apply JUDGE_DB --local
wrangler dev --ip 127.0.0.1 --port 8787 --var SUBMISSIONS_OPEN:false --var JUDGING_ENABLED:false
```

この例は受付と採点を停止した画面確認用です。

`npm run test:worker` は一時的なローカルworkerdでメモリ待機・Git取得・D1復元へ別リクエストを8件ずつ送り、32件の成功を検証します。GitとD1はオフラインfixtureで、APIキーや外部サービスの変更は不要です。`npm run test:worker -- --timeout` は実時間120秒の待機上限と、その後の回復も確認します。試験用プロセスと一時ファイルだけを終了・削除し、開発用サーバーは維持します。

有料の採点校正は、指定の `OPENAI_API_KEY_20261018_HACKATHON` だけを既存Environmentから注入して実行します。既定はDecisionsを各例2回、Sol lowを1回です。予算を事前予約し、失敗時の不明な費用予約も残します。期待点や校正ラベルはAPIへ送りません。現行の結果は [v4検証記録](docs/scoring-conditions-v4.md)、過去版の結果は [v3校正記録](docs/scoring-calibration.md) にまとめます。`--decisions-only` は質問文の反復検証用で、Solの理由生成を省きます。これだけを両APIの検証完了とは扱いません。

```bash
op run --environment "$OP_ENVIRONMENT_ID" -- npm run test:calibration -- --live --budget 3 --output /tmp/devday-scoring-calibration.json
```

## Event operation

1. Googleフォームの提出締切は2026年10月18日17:15です。回答シートの見出しと回答行をコピーします。
2. 審査画面へまとめて貼り付け、チーム名・GitHub URL・デモURL、重複・期限超過・不正な入力を確認します。メールアドレスと不要な列はブラウザ内で除外し、サーバーへ送りません。
3. 17:30以降に本番の一括審査を開始します。開始時刻と提出期限はサーバー側でも検証します。本番はmedium固定、検証はlowが既定です。
4. 全件のコミット固定後に最大8件ずつ採点します。完了結果と10位同点を確認し、CSV・JSONを書き出します。

ログインやトークンの手入力はありません。開始ボタンを重ねて押したり同じリクエストを再送しても、同じbatch IDでは審査を二重に作りません。

チーム名とデモURLは登録後にも補足編集できます。評価対象リポジトリ、コミット、点数、API費用は変更せず、再採点しません。発表モードは開始時点の表示内容と結果を固定するため、補足編集は発表開始前に済ませます。

採点キーは `OPENAI_API_KEY_20261018_HACKATHON` です。既存1Password EnvironmentからWorker secretへ非表示のpipeで設定済みです。設定値をリポジトリ、URL、画面へ記載しません。受付と採点の停止は `SUBMISSIONS_OPEN: false` と `JUDGING_ENABLED: false` で反映します。

初回試験は [influ-quest](https://github.com/schroneko/influ-quest)、攻撃試験は [judge-injection-playground](https://github.com/schroneko/judge-injection-playground) を使い、検証区分へ登録します。

検証枠は、本番順位に含めない動作確認用リポジトリの登録件数です。API費用の上限とは別で、登録は140件、費用は$40に制限します。過去の検証結果と費用履歴は保持し、同じリポジトリの重複登録は拒否します。[手元確認用の30件](docs/manual-validation-30.tsv) は、登録先を「検証」にして見出し行ごと貼り付けます。デモURLは空欄です。

公開環境での30件検証には `node scripts/verify-judging-batch.mjs --input /absolute/input.json --output /absolute/report.json --budget 20 --effort medium --live` を使います。入力は異なる公開リポジトリ30件の `{repoUrl, teamName, demoUrl}` 配列です。`--live` を付けない既定動作ではネットワークを使いません。受付前にUUIDと本文を保存し、再実行でも同じレポートを使います。受付結果が不明でも新規受付や仕事の再試行はせず、同じ受付IDを観測します。点数・20条件・確率・ソースSHA/hashが理由生成で変わらないこと、日本語の理由、medium、全件の完了、所要秒数を確認します。`--budget` は結果に返った費用の観測値に対する検証条件で、受付済み処理を止める上限ではありません。実際の課金前停止はWorkerのD1費用台帳で行います。

イベント後は受付と採点を停止してCSV・JSONを書き出します。データの保存期間はイベント後90日を目安とし、削除する対象と影響は別途確認します。
