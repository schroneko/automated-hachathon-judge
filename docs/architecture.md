# Architecture

## Request flow

1. Googleフォームの回答シートを見出しごと最大30件貼り付けます。ブラウザ内で提出日時・チーム名・公開GitHub URL・デモURLを抽出し、メールと不要な列を除外します。
2. 締切、重複、URLをプレビューし、17:30以降に本番審査を一括開始します。Workerも17:15締切と17:30開始、入力、区分別件数、重複を検証します。ログインやトークン入力はありません。
3. batch IDと内容をD1へ原子的に保存し、Queueへコミット固定のメッセージを送ります。同じIDと同じ内容の再送は読み取りだけで返し、内容の違う再送は拒否します。
4. consumerが公開Git smart HTTP refs広告から全件のdefault branchとHEAD SHAを解決し、全件の固定情報を保存します。全件の保存が終わるまで採点メッセージを送りません。各リポジトリの観測時刻を記録し、完全に同時刻のsnapshotとは扱いません。
5. 公開Git smart HTTPの部分取得で固定SHAのcommit・treeを取得し、不要物を除いた対象blobを全文読みます。参加者の除外設定やGit属性を適用せず、匿名REST APIのIP共有クォータ、GitHub token、リンク巡回、対象コードの実行も使いません。
6. 両モデルの入力トークン数を公式APIで計数し、容量と費用予約の範囲を確認します。全文をD1の分割BLOBへ不変保存してから、費用予約とDecisions APIの採点を実行します。4観点の段階点は `choice` で1つずつ選び、攻撃の確率も返します。平均や丸めを点数に使わず、合計はアプリが計算します。
7. consumerが点数・固定証拠・採点日時を保存して順位へ反映し、別Queue `devday-judge-explanations-20261018` へ理由生成を送ります。採点Queueを理由待ちにしません。
8. 理由生成consumerがD1内の固定証拠と点数を読み、別の費用予約後にSolで理由を生成します。本番はmedium、検証はlowが既定です。モデルへツールは渡しません。点数・合計・攻撃判定・SHAの変更は拒否し、根拠が不足する場合は要確認にします。
9. usageを精算し、理由を保存します。理由の失敗でも点数と順位を保持し、明示的な再試行で理由だけを生成し直します。両Queueは各最大8並列、batch 1、自動再試行0です。外部callback endpointやローカルspoolはありません。ブラウザを閉じても処理が続きます。

## Rubric

[単一のルーブリック定義](../src/shared/rubric.ts) を画面、Decisions API、理由生成プロンプトで共有します。版は `2026-10-18-v2`、各観点は `0 / 2 / 4 / 6 / 8 / 10` の6段階、合計40点です。

実装の証拠で段階の条件をすべて満たす最高点を選びます。8点には6点の全条件、10点には8点の全条件が必要です。各理由は根拠と次の段階に不足する条件を示し、10点では最高段階を満たした根拠を示します。READMEの自己申告だけで加点しません。実装ファイルのない提出は機械的に選考対象外とし、Decisionsの点数は書き換えません。操作性はソースから読み取れる範囲で評価します。

## Trust boundary

リポジトリ名、パス、README、コード、refs広告とGitオブジェクトは信頼しない入力です。開発者メッセージへリポジトリ本文を埋め込みません。公式の観点とDevDay参照情報はアプリ側から与えます。

PACKは圧縮16MiB・展開32MiB・単一オブジェクト4MiB・50,000エントリー・パス1,024文字・深さ64を制限し、取得開始から45秒以内に終端まで検証します。危険なパス、リンク、外部submoduleを辿りません。オブジェクトSHA、PACKのチェックサムとdelta復元を検証します。取得と展開は同じisolate内で同時に1件とし、モデル呼び出しの最大8並列は維持します。

大きな全文を同時に複製してWorkerのメモリを使い切らないよう、isolate内に96MiBの処理用予約枠を設けます。取得・復元前に64MiBを確保し、全文が確定したら保存byte数の16倍（2〜64MiB）に減らし、処理終了時に解放します。通常の小さな提出は8並列を維持し、大きな提出だけ同時実行を絞ります。D1のBLOBも1チャンクずつ復元し、全文の数値配列を同時保持しません。

3経路の順番待ちで共有するのはticketと数値状態だけです。各リクエスト自身のタイマーで起床し、最大120秒で待機を終了します。他リクエストのresolverやPromiseに継続を預けません。別invocationを8件同時に呼ぶworkerd検証で、メモリ待機・Git取得・証拠復元を確認します。

依存物、生成物、バイナリ、lockfile、秘密情報ファイルを信頼済みの固定ルールで除外します。残りのUTF-8テキストを最大2,000ファイル・合計3MiBで全文収集し、未知の拡張子も対象にします。ファイル単位の途中切り、先頭ファイルだけの選択、実装を削るコード圧縮は行いません。容量超過や未解決LFS実装は部分採点せず、要確認で停止します。両APIの入力は公式トークン計数で確認し、入力上限と理由用の余裕を超える場合も採点しません。

攻撃判定が低くてもリポジトリ内の指示へ従いません。攻撃判定の失敗、refusal、不正な応答、未知の観点、分布の不整合は審査失敗にします。段階の選択と理由の説明は同じルーブリックを使います。理由モデルへ点数の正当化を強制せず、根拠不足を要確認として返させます。

観点と合計の整合性、許可した段階点、証拠パス、commit SHA、具体的なモデル名をアプリ側で検証します。攻撃スコアと費用情報をモデルへ生成させません。攻撃確率80%以上の結果だけ「攻撃 XX点」を表示し、合計点と順位には加えません。

APIキーは既存1Password Environmentから取得したイベント専用キーをWorker secretとして扱い、ブラウザへ返しません。Cloudflare認証にはWranglerの既存OAuthセッションだけを使います。

## Storage and recovery

既存の共有D1 `wordplay-arcade-budget` に、専用の `devday_judge_` 接頭辞を付けたテーブルで審査状態、結果、区分別費用台帳、API予約を保存します。既存サービスのテーブルとデータは変更しません。新規D1の作成は不要です。旧Durable Objectのmigrationと拒否用classだけを履歴として残し、bindingや旧namespaceへの呼び出しを置きません。

全文の固定証拠は最大4MiBを512KiBずつ最大8個のBLOBに分け、manifestと同じD1 transactionで保存します。SHA、全文hash、byte数、分割順序と完了状態を検証して復元します。同じ提出の再試行は同じ保存済み証拠を再利用し、全文の重複コピーを作りません。旧方式の証拠は履歴として保持し、全文取得済みとは表示しません。APIの公開結果にはソース本文・分割BLOB・内部認証情報を含めません。

条件付きclaimとメッセージの試行番号で重複配信を拒否します。登録済みリポジトリの再登録、完了結果の取得、処理済みメッセージの重複配信は書き込み0件です。新規登録は本番40件・検証40件、各審査は最大3試行で、採点メッセージの送信は合計最大240回です。コミット固定用のメッセージもbatch単位で上限を設けます。

失敗した採点を自動でキューへ戻しません。失敗や30分以上進まない処理を確認して明示的に再試行します。採点前の失敗は採点を、採点済みの理由失敗は理由だけを再試行します。検証区分で理由の推論強度を変更しても点数を変更しません。過去のAPI費用精算と未確定の予約は保持し、本番$90・検証$20の上限へ含めます。

5分以上停止した処理には、API予約履歴0件・証拠保存0件・結果なしの場合だけ、明示的な復旧を1回許可します。callback世代を回転し、専用メッセージで同じattempt・SHAを続行します。以前のhandlerは予約・保存・確定できません。通常のattemptと送信履歴を減らさず、復旧の送信回数を別に記録します。予約が1件でもあれば、未精算・精算済みのどちらでもこの復旧経路を使えません。

再試行はbatchで固定したSHAとbranchを保持します。固定後にHEADやdefault branchが変わっても評価するコードを変更しません。固定時点で非公開、空、default branch不明だった結果も保持し、あとから別の版を評価し直しません。

登録後のチーム名とデモURLは専用の更新経路で補足できます。採点状態、コミット、費用、処理時刻を保持し、Queueを送信しません。同じ値への更新は書き込み0件です。デモURLはHTTPまたはHTTPSだけを受け付け、認証情報、制御文字、バックスラッシュを拒否します。

## Before and after

| 項目 | 変更前 | 現在 |
| --- | --- | --- |
| 状態保存 | Durable Objectのmetaとjob key | 共有D1内の審査専用テーブル |
| 実行 | ローカルRunnerがclaimとheartbeatを定期送信 | Queue consumerが有限のjobを処理 |
| 起動 | 個別登録後にRunnerが取得 | 回答シート一括取り込み後に一括開始 |
| 評価対象 | 各jobの採点開始時に解決 | 全件のコミットを最初に固定 |
| 並列数 | Runnerの10slot | クラウドで最大8件 |
| 会場端末 | Runner実行環境への依存 | ブラウザだけ |
| 待機中の書き込み | heartbeatによる状態更新 | 空のQueueと結果取得は書き込み0件 |

`JUDGING_ENABLED: false` は新しい採点開始とAPI予約を拒否し、実行済みの精算・結果保存を許可します。`SUBMISSIONS_OPEN: false` は新規登録を停止します。APIへ送信済みの要求が停止フラグだけで取り消されるとは扱いません。

イベント後は書き出しを保管し、D1の保存期間は90日を目安とします。削除対象と影響を別途確認し、共有D1や旧Durable Objectを自動削除しません。

10位同点が境界をまたぐ場合は全員を確認候補にします。表示順で勝者を確定しません。
