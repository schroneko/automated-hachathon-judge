## Selected services

Workersで画面とAPIを提供し、既存の共有D1 `wordplay-arcade-budget` の `devday_judge_` テーブルだけを使います。新しいD1の作成枠は不要です。他サービスの既存テーブル・データは変更しません。

採点Queue `devday-judge-20261018` と理由生成Queue `devday-judge-explanations-20261018` に審査ID等の有限メッセージを送り、Workerのconsumerで処理します。Decisionsの点数を先に保存し、Solの理由生成の完了を待たずに表示します。採点と理由生成は別Queueで進み、両段階ともメモリ入場制限を受けます。ブラウザを閉じても処理が続きます。Durable ObjectsとBrowser Renderingは使用しません。旧Durable Objectのmigration履歴と拒否用classだけを保持します。

公開Git smart HTTP refs広告でdefault branchとSHAを固定し、部分取得でcommit・treeと必要なblobを読みます。匿名REST APIのIP共有クォータには依存しません。refsは最大256KB、PACKは圧縮16MiB・展開32MiB・単一オブジェクト4MiB・50,000エントリーです。不要物を除いた対象UTF-8テキストを最大2,000ファイル・合計3MiBで全文取得します。途中切りや参加者の除外設定は使いません。GitHub token、対象コードの実行、リンク巡回は不要です。

画面のログインやトークン入力はありません。採点キーは既存1Password Environmentの `OPENAI_API_KEY_20261018_HACKATHON` をWorker secretへ非表示のpipeで設定済みです。ブラウザへ渡しません。

## Bounds and cost

| 項目 | 上限 |
| --- | --- |
| 登録 | 本番40件、検証140件、合計180件。一括最大30件 |
| 試行・送信 | 初回と主催者の明示的な再試行を合わせて1件につき最大3回 |
| 採点の通常チェーン開始 | 1件につき最大3回、合計最大540件。審査IDなどのmetadataだけ |
| 理由生成チェーン開始 | 1件につき最大3回、合計最大540件 |
| コミット固定の制御送信 | batchにつき最大3回、合計最大540件 |
| 課金前停止の復旧チェーン開始 | 各提出につき最大1回、合計最大180件。過去のAPI予約・証拠保存が0件の場合のみ |
| Consumer | 両Queueともbatch 1、最大同時8件、自動再試行0 |
| メモリ不足の遅延再配送 | 各チェーン最大360回、1回5秒。挿入する遅延は合計最大1,800秒・30分 |
| GitHub取得 | 入場後の取得全体45秒。取得ゲートの入場待ちは別途最大120秒 |
| 固定証拠 | 最大4MiB、512KiBずつ最大8分割。各提出で1個を再利用 |
| OpenAI採点 | 各API呼び出し最大180秒 |
| OpenAI費用 | 予約を含め本番$90、検証$40 |
| Queue保持 | Workers Freeの24時間 |
| 結果・費用台帳 | イベント後90日を目安。削除は別途確認 |

旧420件は合計140提出×3の基礎上限です。現在は合計180提出×3で、採点・理由生成・コミット固定それぞれ最大540件です。これは初回・明示的な再試行のチェーン開始または制御送信の上限で、メモリ不足の再配送を含むQueueメッセージ総数ではありません。新規batchには少なくとも1件の新規審査が必要なため、batch数も最大180です。復旧180件を加えた基礎配送数は最大1,800件で、メモリ不足の再配送前の値です。

採点・理由生成・復旧ではclaim前に `tryAcquireJudgingMemory` で即時に入場を試みます。空きがなければ同じメッセージの `memoryDeferrals` だけを1増やし、5秒遅延でQueueへ送り、現在の呼び出しを終了します。メモリ待ちのためconsumer枠を保持してsleepしません。通常の遅延再配送はOpenAI API呼び出し・費用予約・試行回数や通常dispatchの増加・D1書き込みがすべて0件で、既存のソースSHAと識別子を保持します。360回の上限到達または再配送失敗時にだけ、現在の状態・識別子が一致する条件付き更新で失敗状態を一度保存します。理由生成の失敗では固定点を保持します。作業停止時は再配送を止め、新しいAPI処理を開始しません。

各通常試行・理由生成dispatch・復旧はそれぞれ独立したチェーンです。各チェーンの挿入遅延は最大 `360 × 5 = 1,800` 秒ですが、Queue自体の滞留時間は別で、この30分には含みません。初回配送を含むアプリ生成の仕事配送上限は `180 ×（3採点 + 3理由生成 + 1復旧）× 361 = 454,860` 件です。コミット固定の制御メッセージ最大540件と、Queueサービス自身のat-least-once重複配送は別に加わります。メモリ不足でも遅延配送に伴う有限のQueue操作と費用が生じます。これらのアプリ生成数はアカウント全体の利用量・費用のhard limitではなく、他サービスの利用量も含みません。処理済みの重複配送は条件付きclaimで再処理を拒否します。

各Queueの最大同時8件はモデル呼び出し8並列の保証ではありません。isolateごとのメモリ入場予算96MiBに対し、初期予約は64MiB、スナップショット確定後は2MiBとシリアライズ後バイト数の16倍の大きい方へ減らします。大きな入力では実際の同時実行数を抑えます。これは予約量の会計であり、実測heapや128MiBでの強制終了防止を保証するものではありません。120秒待つ `acquireJudgingMemory` は補助処理・ローカルfixture用で、本番Queueのメモリ入場経路には使いません。Git取得とD1復元の入場ゲートには、別にリクエストごとの最大120秒の待機タイマーがあります。D1クエリ自体のtimeoutではありません。

変更のないリクエスト、空のキュー、重複登録、処理済みメッセージの重複配信はD1書き込み0件です。常駐ポーリング、定期heartbeat、Cronはありません。検証枠の拡大や再試行でも既存結果、費用台帳の精算・未確定予約、試行・送信履歴を保持し、同じ区分の上限へ含めます。`0010_validation_capacity.sql` は検証予算上限だけを$40へ引き上げます。登録上限・送信上限・試行上限・費用予約・停止フラグをテストしてから公開します。

本番はSolのmedium、検証はlowが既定で、検証区分ではmediumとhighも選べます。Decisionsはルーブリック `2026-10-18-v4` の20条件をnative predicateで個別判定し、確率が0.8以上の条件から最高連続段階をコードで採点します。実装ファイルのない提出は選考対象外です。両モデルは同じSHA・同じ全文を読み、Solは点数・条件・評価対象・監査情報を変更できず、既存の `reviewRequired` も解除できません。採点の詳細は [審査方法](judging-method.md) を参照してください。過去のv2・v3結果と理由再生成は当時の基準を保持します。

採点済みの `reviewRequired` は情報として「確認メモ」と表示します。運用者の操作は不要で、確定点・順位・通過判定を変更せず、人の確認を通過条件にしません。未採点のソース取得・入力・API・容量の失敗は別のエラーです。理由生成だけの失敗では確定点を保持します。

採点前に公式APIで両モデルの入力トークンを計数します。入力上限922,000トークンと説明用の余裕を確認し、長文料金の割増を含めて予約します。容量不足は未採点エラーとして停止し、黙ってソースを切りません。

料金・制限の確認元: [Queues pricing](https://developers.cloudflare.com/queues/platform/pricing/)、[Queues limits](https://developers.cloudflare.com/queues/platform/limits/)。

## Setup and stop

Wranglerの既存OAuthセッションを使います。1Passwordはアプリ用OpenAIキーの取得にだけ使い、Cloudflare用credentialは取得・注入しません。

Queueは作成済みで、共有D1には審査専用migrationを適用します。新規D1やQueueを毎回作成しません。正規の公開手順は [Deployment](deployment.md) にまとめます。

受付停止は `SUBMISSIONS_OPEN: false`、採点停止は `JUDGING_ENABLED: false` です。採点停止は新しいclaimとAPI費用予約を拒否し、実行済みAPIの精算・結果保存は許可します。停止設定は正規の `wrangler deploy` で反映します。未確定の費用予約を解放して再開しません。

公開に失敗した場合は受付と採点を停止状態に保ち、以前の停止済みWorkerへ戻せるよう公開versionを記録します。D1の新しいテーブルや旧Durable Objectのnamespaceを削除するrollbackは行いません。イベント後は書き出しを保管し、90日を目安に審査専用データの削除対象と影響を別途確認します。
